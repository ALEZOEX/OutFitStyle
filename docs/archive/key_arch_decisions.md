# Ключевые архитектурные решения (KAD)

## ADR-001: Использование микросервисной архитектуры

**Статус**: Принято

**Контекст**: 
Необходимо разработать масштабируемую и поддерживаемую систему для рекомендаций одежды.

**Решение**:
Разделить приложение на независимые микросервисы:
- Go API-сервер для бизнес-логики
- Python ML-сервис для рекомендаций
- База данных PostgreSQL для хранения данных

**Последствия**:
- Повышенная масштабируемость
- Независимое развертывание
- Разные технологии для разных задач

## ADR-002: Использование единой модели вещей

**Статус**: Принято

**Контекст**:
Необходимо унифицировать хранение и обработку вещей из разных источников.

**Решение**:
Создать единую таблицу `clothing_items` с расширенными атрибутами и полем `source` для указания происхождения.

**Последствия**:
- Упрощение логики выборки
- Единый подход к обработке
- Возможность приоритезации источников

## ADR-003: Использование Service Mesh (Istio)

**Статус**: Принято

**Контекст**:
Необходимо упростить управление сетевым взаимодействием между сервисами.

**Решение**:
Внедрить Istio Service Mesh для управления трафиком, безопасности и наблюдаемости.

**Последствия**:
- Централизованное управление трафиком
- Автоматическое шифрование mTLS
- Улучшенная наблюдаемость

## ADR-004: Event-driven архитектура для рекомендаций

**Статус**: Принято

**Контекст**:
Необходимо обеспечить асинхронную обработку рекомендаций для повышения производительности.

**Решение**:
Использовать Apache Kafka для публикации и потребления событий рекомендаций.

**Последствия**:
- Асинхронная обработка
- Повышенная отказоустойчивость
- Масштабируемость обработки

## ADR-005: Разделение Retrieval и Ranking

**Статус**: Принято

**Контекст**:
Необходимо оптимизировать процесс генерации рекомендаций.

**Решение**:
Разделить процесс на два этапа: Retrieval (подбор кандидатов) и Ranking (ранжирование).

**Последствия**:
- Более эффективный поиск
- Возможность разных стратегий для разных этапов
- Лучшая производительность
